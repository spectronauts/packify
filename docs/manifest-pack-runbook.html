What this covers

A manifest-based pack wraps plain Kubernetes YAML — CRDs, operators, policy, anything kubectl apply would take — so Palette can version it, template it, and roll it out through cluster profiles. No Helm chart required.

The path from a folder of YAML to a running workload crosses four systems. Each hand-off has its own address format, and they are not interchangeable — that is where most first attempts fail.

01

Anatomy of a manifest pack

What Palette actually consumes, and what each file is for.

Where a Helm pack points at a chart, a manifest pack carries the YAML itself — anything kubectl apply would take. Palette adds versioning, templating, and lifecycle on top. A pack is four parts:

A complete pack, built from two source files
hello-app-1.0.0/
├── manifests/
│   ├── deployment.yaml   # your YAML, copied verbatim
│   └── namespace.yaml
├── pack.json             # metadata + apply order
├── values.yaml           # the pack's public API
└── README.md             # shown in the Palette UI

manifests/ — your YAML, untouched

Copied in verbatim, templating and all. Manifests are Go templates, rendered by Palette at deploy time. Plain YAML with no {{ }} works fine — templating is opt-in.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  namespace: "{{ .Values.namespace }}"
spec:
  replicas: {{ .Values.replicas }}
apiVersion: v1
kind: Namespace
metadata:
  name: "{{ .Values.namespace }}"

pack.json — the metadata Palette indexes

kubeManifests is the field that matters: it is both the file list and the apply order. Palette applies top to bottom, which is how CRDs land before the operator that needs them.

pack.json
{
  "addonType": "app services",
  "displayName": "Hello App",
  "kubeManifests": [
    "manifests/deployment.yaml",
    "manifests/namespace.yaml"
  ],
  "layer": "addon",
  "name": "hello-app",
  "version": "1.0.0"
}

values.yaml — the knobs users turn

This is what someone edits in the profile builder. It is the pack's entire public API.

values.yaml
pack:
  spectrocloud.com/display-name: Hello App
  namespace: hello
  content:
    images:
      - image: nginx:1.27

manifests:
  deployment:
    namespace: "hello"
    replicas: 2
  namespace:
    namespace: "hello"

Two halves. pack: holds pack-level settings, including content.images for airgap and Edge mirroring. manifests: holds one key per file, named after its basename.

Values are scoped per manifest

Values under a manifest's key belong to that manifest alone. That is why the deployment above writes {{ .Values.namespace }} and not {{ .Values.manifests.deployment.namespace }} — each file is rendered against its own block.

Every referenced value must exist

Rendering fails on a missing value. The deployment references both {{ .Values.namespace }} and {{ .Values.replicas }}, so both keys must appear under deployment:.

manifestify auto-generates only namespace. The replicas: 2 above was added by hand — every other parameter your manifests template is yours to add, and it is the step most easily forgotten.

readinessCheck — gating on cluster state

An optional top-level block, a sibling of pack: and manifests: rather than a child of either. It tells Palette to wait until a resource reports a given state before treating the pack as deployed, which is how you stop the next pack in a profile from starting too early.

pack:
  namespace: monitoring

readinessCheck:                # top level, not under pack:
  v1beta1:
    - name: "prometheuses-crd"
      kind: "CustomResourceDefinition"
      group: "apiextensions.k8s.io"
      version: "v1"   # cluster-scoped, so no namespace
      keysToCheck:
        - keyToCheck: "status.conditions[0].status"
          expectedValue: "True"

manifests:
  crd-prometheuses: {}
pack:
  namespace: monitoring

readinessCheck:
  v1beta1:
    - name: "prometheus-operator"
      namespace: "monitoring"   # namespaced, so it is required
      kind: "Deployment"
      group: "apps"
      version: "v1"
      keysToCheck:
        - keyToCheck: "status.availableReplicas"
          expectedValue: "1"

manifests:
  operator: {}

Add namespace to an entry when the kind is namespaced. Cluster-scoped kinds, CRDs among them, omit it.

FieldMeaning
nameLabel for the check, and the resource name to look up
kind / group / versionIdentify the resource type, e.g. CephCluster / ceph.rook.io / v1
namespaceOnly for namespaced kinds
keysToCheckA list of keyToCheck and expectedValue pairs, so one resource can assert several conditions
keysToCheck is a list

The pair goes inside a keysToCheck entry, not flat alongside kind and group. A flat keyToCheck / expectedValue at the item level is a common mistake and will not match.

Undocumented field

readinessCheck appears in neither the pack.json JSON schema nor the pack-constraints reference. The shape above is taken from a live cluster's Pack custom resource, so treat the field names as observed rather than specified, and confirm with Spectro Cloud before relying on it in production.

How it renders

At deploy time Palette takes each manifest, renders it against its own block from values.yaml, and applies the results in kubeManifests order. So namespace: "{{ .Values.namespace }}" becomes namespace: "hello" on the cluster.

02

Build the pack

Turn a directory of Kubernetes YAML into the four files Palette expects.

Palette requires a specific shape: a manifests/ directory, a pack.json listing every file under kubeManifests, and a values.yaml exposing per-manifest parameters. manifestify.sh assembles all of it.

Build
bash manifestify.sh \
  -n prometheus-operator-crds \
  -v 0.76.2 \
  -p addon \
  -a monitoring \
  -s monitoring \
  -m .manifests/crd \
  -d "Prometheus Operator CRDs" \
  -r .manifests/pack-readme.md

The result is ./prometheus-operator-crds-0.76.2/:

Output
prometheus-operator-crds-0.76.2/
├── manifests/          # your YAML, copied verbatim
├── pack.json           # kubeManifests list + layer metadata
├── values.yaml         # per-manifest parameters
└── README.md           # from -r, or a generated stub

Flags that matter

FlagEffect
-mA file or a directory. Repeatable. Directories are not searched recursively — point at the exact folder holding the YAML.
-fA text file listing manifest paths, one per line. Use this when apply order matters.
-rThe pack's README. Without it a stub is generated; a README.md in your working directory is never picked up by accident.
-zAlso produce <name>-<version>.tar.gz, ready to push by hand.
-FOverwrite an existing pack directory. Preserves a logo.png or hand-edited README.md already inside it.
Manifest names come from filenames

Each file becomes a key under manifests: in values.yaml, named after its basename. Two files called config.yaml in different source folders will collide, and the build stops with a duplicate-name error. Rename one, or pass files individually.

Namespace values

A namespace value is emitted only for manifests that actually template {{ .Values.namespace }}. Cluster-scoped resources such as CRDs get {} instead, so the key is present without a misleading value. Pass -N to suppress it everywhere.

03

Push to Artifactory

Archive the pack and push it as an OCI artifact under the path Palette looks in.

Palette expects a gzipped tarball, tagged with the version, under a spectro-packs/archive path. The spectro CLI is deprecated; oras is the supported route.

Build and push in one command
bash manifestify.sh \
  -n prometheus-operator-crds \
  -v 0.76.2 \
  -p addon \
  -a monitoring \
  -s monitoring \
  -m .manifests/crd \
  -d "Prometheus Operator CRDs" \
  -r .manifests/pack-readme.md \
  -R artifactory.teams.jfrog.com/jarvis-pack-manifests/pavan-packs \
  -L -P

-L runs oras login, -P archives and pushes. Doing it by hand is three commands:

Manual equivalent
oras login artifactory.example.com

# archive from the parent, so the pack directory is the tarball root
tar -czvf prometheus-operator-crds-0.76.2.tar.gz prometheus-operator-crds-0.76.2

oras push --image-spec v1.0 \
  artifactory.example.com/my-repo/my-packs/spectro-packs/archive/prometheus-operator-crds:0.76.2 \
  prometheus-operator-crds-0.76.2.tar.gz

Two addresses, one registry

This is the most common source of confusion. The address you push to is not the endpoint you give Palette.

Used byAddress
oras — pushing artifactory.example.com/my-repo/my-packs
Palette — reading https://artifactory.example.com + suffix /artifactory/api/docker/my-repo

oras is a Docker V2 client and always requests /v2/<repo>/…. Artifactory's /artifactory/api/docker/<repo>/ path is a server-side endpoint that Palette uses over plain HTTP. Both reach the same artifact; neither works in the other's position.

Never re-push a version

Palette caches the manifest digest it saw when it synced the registry. Re-pushing the same tag moves it to a new digest and leaves Palette requesting one that no longer exists — cluster reconciles then fail with not found in a loop.

Gzip embeds a timestamp, so even rebuilding identical content produces a different digest. Treat a pushed version as immutable and bump the version instead.

What it looks like in Artifactory

After a successful push, the repository browser shows the pack nested under the path Palette expects. Every segment comes from somewhere specific:

Repository browser — jarvis-pack-manifests
jarvis-pack-manifests            ← repository key
├── .jfrog                         Artifactory internal
└── pavan-packs                  ← base_content_path
    └── spectro-packs            ← Palette convention
        └── archive
            └── prometheus-operator-crds   ← pack name
                ├── 0.76.1       ← tag = pack version
                ├── 0.76.2
                └── _uploads       Artifactory staging

One tag per pushed version, side by side. This is the immutability rule made visible: 0.76.1 and 0.76.2 coexist rather than one replacing the other.

Repository settingValue
Package TypeOCI — a Docker or generic repo will not serve the V2 API
Repository Layoutsimple-default
File URLhttps://artifactory.teams.jfrog.com/artifactory/jarvis-pack-manifests/
Cross-check against Terraform

The tree confirms the registry fields in step 04. pavan-packs is the base_content_path, and spectro-packs is absent from every Terraform field because Palette appends it when reading.

Verify before moving on

Confirm the artifact landed
REPO=artifactory.example.com/my-repo/my-packs/spectro-packs/archive/prometheus-operator-crds

oras repo tags $REPO
oras manifest fetch --descriptor $REPO:0.76.2
04

Register in Palette

Create the OCI pack registry with the spectrocloud_registry_oci resource.

registry.tf
resource "spectrocloud_registry_oci" "packs" {
  name       = "customer-pack-registry"
  type       = "basic"
  endpoint   = "https://artifactory.example.com"
  is_private = true

  # JFrog serves its Docker V2 API under a per-repo path
  endpoint_suffix = "/artifactory/api/docker/my-repo"

  # directory inside the repo holding the packs; "" for the repo root
  base_content_path = "my-packs"

  provider_type      = "pack"
  is_synchronization = true

  credentials {
    credential_type = "basic"
    username        = var.artifactory_user
    password        = var.artifactory_token
  }
}

Field by field

FieldValueWhy
typebasicAnything that is not ECR. Artifactory, Harbor, GitLab.
provider_typepackDefaults to helm. Packs will not appear without this.
is_synchronizationtrueMandatory when provider_type = "pack".
base_content_pathdirectoryRequired whenever sync is on.
endpoint_suffixAPI pathAppended to endpoint. JFrog-specific.
credential_typebasicAlso accepts secret, sts, noAuth.
Two provider validations will stop your apply

provider_type = "pack" with is_synchronization = false is rejected outright. So is is_synchronization = true without a base_content_path.

Synchronization also cannot be turned off later — the provider blocks changing it from true to false as a day-2 operation.

Do not include spectro-packs

Palette appends spectro-packs itself. It belongs in your oras push target, never in endpoint, endpoint_suffix, or base_content_path.

Use an Artifactory identity token rather than an account password — Artifactory rejects passwords when SSO is enabled.

Apply
terraform init
terraform apply

Self-signed certificate? Add a tls_config block inside credentials with a certificate. insecure_skip_verify = true exists but disables verification entirely — keep it out of customer environments.

05

Sync and verify

Palette reads the registry and indexes every pack it finds.

With is_synchronization = true, Palette syncs on creation and on a schedule after that. It walks base_content_path, finds spectro-packs/archive, and registers each tag as a pack version.

wait_for_sync does not apply here

The provider's wait_for_sync argument only takes effect for provider_type of helm or zarf — not pack. Terraform will return before the first sync finishes, so verify in the UI or by data source rather than assuming apply completing means the pack is available.

Confirm the pack is indexed

registry-lookup.tf
data "spectrocloud_registry_pack" "packs" {
  name = "customer-pack-registry"
}

data "spectrocloud_pack" "crds" {
  name         = "prometheus-operator-crds"
  version      = "0.76.2"
  registry_uid = data.spectrocloud_registry_pack.packs.id
}

output "pack_uid" {
  value = data.spectrocloud_pack.crds.id
}
Do not set type = "manifest"

type accepts manifest, but the provider short-circuits that case and returns without performing any lookup, leaving every attribute null. The failure surfaces much later as The argument "pack.0.name" is required on the cluster profile, pointing at the wrong file.

Name, version, and registry_uid identify the pack on their own.

A UID in the output means Palette has indexed the pack and it is ready to reference. An empty result means sync has not completed or has not found the artifact.

Sync troubleshooting

Registry connects but no packs appear — base_content_path is wrong. Palette syncs only at that exact directory level: not the repo root, not nested children.

Packs appear under the wrong type — provider_type is still helm.

Authentication failures — the token lacks read access to the repository, or SSO is rejecting a password.

You can also confirm in the UI under Tenant Settings → Registries, which shows sync status and the last sync time.

06

Create the profile

Wrap the pack in an add-on cluster profile.

Packs reach clusters through profiles. For something added to existing clusters, that means an add-on profile.

profile.tf
resource "spectrocloud_cluster_profile" "crds" {
  name        = "prometheus-operator-crds"
  description = "Prometheus Operator CRDs"
  type        = "add-on"
  cloud       = "all"
  version     = "1.0.0"

  pack {
    name   = data.spectrocloud_pack.crds.name
    tag    = data.spectrocloud_pack.crds.version
    uid    = data.spectrocloud_pack.crds.id
    values = data.spectrocloud_pack.crds.values
  }
}

Taking values straight from the data source uses the pack's defaults. To override a parameter, supply your own YAML instead — the structure mirrors the values.yaml from step 2:

Overriding values
  pack {
    name   = data.spectrocloud_pack.crds.name
    tag    = data.spectrocloud_pack.crds.version
    uid    = data.spectrocloud_pack.crds.id
    values = <<-EOT
      pack:
        namespace: monitoring
      manifests:
        crd-prometheuses: {}
        crd-servicemonitors: {}
    EOT
  }

Profiles are versioned in their own right. Publishing a new pack version means bumping the profile version too, which is what gives you a rollback point.

07

Attach to a cluster

Deploy the add-on profile onto a running cluster.

deploy.tf
resource "spectrocloud_addon_deployment" "crds" {
  cluster_uid = var.cluster_uid
  context     = "project"

  cluster_profile {
    id = resource.spectrocloud_cluster_profile.crds.id
  }
}

On apply, Palette's cluster agent pulls the artifact from Artifactory by digest, unpacks the tarball, renders each manifest through the values, and applies them in kubeManifests order.

Confirm the rollout

On the cluster
kubectl get crd | grep monitoring.coreos.com

# watch the agent do the work
kubectl logs -n cluster-<uid> deploy/palette-manager -f
If the agent logs "not found"

A failed to download pack … not found loop means Palette is requesting a digest the registry no longer has — the symptom of a re-pushed tag described in step 3. Push a new version, update the profile to reference it, and re-apply. Re-syncing the registry alone will not clear it, because the profile also holds the stale reference.

Demo script

A 20-minute walkthrough. Everything past step 3 is pre-staged.

Have the registry, profile, and a running cluster already in place. Demonstrate the parts that are fast and visual; do not wait on a sync in front of an audience.

0:00
Show the raw YAML. Ordinary CRDs, nothing Palette-specific — the point is that no chart is needed.
2:00
Run manifestify.sh. Sub-second. Open the generated pack.json and values.yaml and show that manifest keys map to filenames.
5:00
Push with -L -P. Show the size drop — a 4.3 MB CRD set compresses to about 455 KB. Confirm with oras repo tags.
8:00
Switch to Artifactory in a browser. Show the artifact under spectro-packs/archive. This is the moment the two-address distinction lands.
11:00
Show registry.tf and the Palette registry already synced. Call out provider_type = "pack" as the field everyone misses.
14:00
Show the pack in the profile builder, rendered values and all — the pack is now indistinguishable from a Spectro-published one.
17:00
terraform apply the add-on deployment against the live cluster. Tail the agent log, then kubectl get crd.
Have a fallback

Pre-push a second version — 0.76.3, say — before the session. If a live push fails on network or auth, switch to the pre-staged version and keep moving rather than debugging in front of the room.

Rules that bite

  • A pushed pack version is immutable. Bump, never overwrite.
  • provider_type = "pack" requires is_synchronization = true.
  • is_synchronization = true requires base_content_path.
  • Synchronization cannot be disabled after creation.
  • wait_for_sync is ignored for pack registries.
  • Manifest basenames must be unique within a pack.
  • Directory collection is not recursive.
  • spectro-packs goes in the push path, never in the Terraform fields.
